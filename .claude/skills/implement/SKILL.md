# Implement (테스트 먼저)

## 0. 전제

- 대상 명세의 상태가 `승인`이어야 한다. 예외는 명세 시나리오대로 동작하지 않는 버그 수정뿐이다(spec 스킬 0단계). 그 밖에는 멈추고 spec 스킬로 간다.
- `git status --short`로 무관한 변경을 확인하고 건드리지 않는다.
- 대상 명세 전체, 건드리는 [불변식](../../../docs/INVARIANTS.md), CLAUDE.md §3·§6·§7을 다시 읽는다.

## 1. 작업 목록

- 새로 생기거나 바뀐 시나리오를 데이터(마이그레이션·타입) → 서버(`lib/`·라우트 핸들러) → 화면(`app/`) 순서로 묶는다(수직 슬라이스).
- 시나리오마다 명세의 테스트 층으로 검증한다.
  - 단위: Vitest node 환경. Supabase 클라이언트·`next/headers`·`next/navigation`·`next/cache`는 `vi.mock`으로 바꾼다. `redirect()`는 던지는 함수로 mock해 리다이렉트 경로를 확인한다.
  - 컴포넌트(jsdom): 파일 첫 줄에 `// @vitest-environment jsdom`을 쓰고 Testing Library로 화면 문구·상호작용을 확인한다.
  - 통합(DB): 실제 DB가 필요하다. 테스트 DB 이름에 `test`가 들어간 곳에서만 돌린다.
  - 수동 확인: 테스트가 없다. 확인 절차를 보고에 적는다.
- 테스트 파일은 소스 옆 `<이름>.test.ts(x)`에 둔다(편집 가드가 이름 짝으로 관련 테스트를 찾는다). 여러 파일에 걸친 시나리오는 제목의 시나리오 ID로 찾는다.

## 2. 시나리오마다 빨강 → 초록 → 정리

1. **빨강**: 테스트 제목은 `<시나리오 ID> <한국어 설명>`이다. `npx vitest run <파일>`로 실행해 **기대한 이유로** 실패하는지 확인한다. import 오류나 오타로 실패한 것은 실패 확인이 아니다.
2. **초록**: 테스트를 통과시키는 최소 구현을 쓴다. 편집 가드가 막으면 메시지대로 한다(코드 경로 밖이면 명세를 고쳐 다시 승인, lib 로직이면 관련 테스트부터).
3. **정리**: CLAUDE.md 규약대로 다듬고 테스트를 다시 돌린다.

- TDD 훅이 편집마다 연관 테스트(`vitest related`)를 돌린다. `[TDD 피드백]`의 실패가 빨강 단계의 의도된 실패인지 회귀인지 판단한다. 테스트 기대값을 바꿔 통과시키지 않는다.
- 명세에 없는 동작이 필요해지면 구현을 멈추고 명세를 고쳐 다시 승인받는다.
- 지운 시나리오 ID를 제목에 가진 테스트는 새 ID로 고치거나 지운다(`spec:check`가 없는 ID 참조를 막는다).

## 3. 마감 점검

- `npm run spec:check`: 새로 생기거나 바뀐 시나리오가 모두 테스트에 연결돼 있다(수동 확인 시나리오는 빼고).
- `npm run lint && npm run typecheck && npm test`를 실행한다. 하네스를 바꿨으면 `npm run test:tooling`을 더한다.
- `npm run build`: Supabase(또는 전환 뒤 DB)에 닿아야 sitemap 프리렌더가 통과한다. 닿지 않아 실패했으면 그 사실을 그대로 보고한다.
- 건드린 불변식마다 명세 §6의 방법대로 테스트가 있다.
- 명세 상태를 바꾼다. 모든 시나리오에 테스트가 있으면 `완료`, 테스트 없는 시나리오가 남으면(기존 테스트 부채, 수동 확인) `현행`이다. 승인 줄의 날짜는 남긴다.
- 로드맵 항목을 마쳤으면 `docs/plans/roadmap.md`를 갱신한다.

## 4. 커밋과 보고

- 커밋은 사용자 요청 뒤 `commit` 스킬로 한다. 시나리오 묶음 단위로 나누고, 구현과 그 테스트는 같은 커밋에 넣는다(커밋 가드가 짝을 확인한다). `--no-verify`를 쓰지 않는다. push는 Vercel 운영 배포라 따로 승인받는다.
- 보고할 것: 시나리오별 테스트와 실패 확인 여부, 명세와 다르게 판단한 점, 수동 확인이 필요한 항목, 범위 밖 발견 사항(명세 §7 후보).
