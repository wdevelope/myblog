# Spec (명세 먼저)

명세(`docs/specs/<기능>.md`)가 기능 동작의 정본이다. 테스트는 시나리오에서 나오고, 구현은 그 테스트를 통과시킨다. 형식과 상태 규칙은 `docs/specs/_template.md`가 정본이다.

- 편집 가드(`.claude/hooks/edit-guard.mjs`)는 승인·현행·완료 명세의 코드 경로 밖 소스(`app/`·`lib/`·`middleware.ts`) 편집을 막는다. pre-commit의 커밋 가드와 `spec:check`가 Bash로 만든 파일까지 다시 잡는다.
- 이 스킬은 명세만 고친다. 소스·테스트는 승인 뒤 `implement` 스킬로 고친다.

## 0. 작업 종류 정하기

고칠 파일 경로로 `grep -n '<경로 일부>' docs/specs/*.md`를 해서 그 파일을 코드 경로로 가진 명세를 찾는다.

- **새 기능**: 어느 명세도 덮지 않는 새 화면·액션이다. 새 명세를 `초안`으로 쓴다(2단계).
- **기존 기능의 동작 변경**: 시나리오 결과가 바뀌거나 시나리오가 새로 생긴다. 명세 §7의 의심 동작을 고치는 것도 여기에 든다. 대상 명세를 고친다(3단계).
- **명세대로 동작하지 않는 버그**: 시나리오 결과는 그대로이고 코드가 어긋난 경우다. 명세를 고치지 않고 `implement` 스킬로 간다(회귀 테스트 제목에 그 시나리오 ID).
- 판단이 서지 않으면 동작 변경으로 보고 사용자에게 확인한다.

## 1. 입력 읽기

- 사용자의 요청, [로드맵](../../../docs/plans/roadmap.md)의 해당 단계, [INVARIANTS](../../../docs/INVARIANTS.md), 관련 명세(§8 관련 코드로 이어지는 명세 포함), 대상 코드.

## 2. 새 기능 초안 쓰기

`_template.md`를 복사해 `docs/specs/<기능-kebab>.md`로 쓴다. 상태는 `초안`, 근거에는 요청 날짜와 요약을 적는다.

- **ID 접두**: 영문 대문자로, 다른 명세와 겹치지 않게 정한다(`grep -h 'ID 접두' docs/specs/*.md`).
- **코드 경로**: 이 기능이 새로 만들 파일·폴더만 적는다. 디렉터리는 `/`로 끝낸다. 승인 상태까지는 아직 없는 경로여도 된다. 다른 명세가 가진 파일(`app/layout.tsx`, `lib/types.ts` 등)을 고치게 되면 코드 경로에 넣지 않고 §8에 적는다. 같은 파일을 두 명세가 덮으면 `spec:check`가 막는다.
- **시나리오**: 템플릿의 "새 기능" 목록을 빠뜨리지 않는다(정상 흐름, 비로그인·일반 사용자·관리자 권한, public·private, 타입 라우팅, 입력 검증, 없는 대상, 캐시 무효화, 클라이언트 로딩·빈 목록·오류). 결과는 관찰할 수 있는 값(반환 객체·오류 문구·리다이렉트 경로·화면 문구·DB 상태)으로 쓰고, 시나리오마다 테스트 층을 정한다.
- §4 계약·§5 데이터·§6 불변식을 채운다. 저장 형태가 바뀌면 새 마이그레이션 계획을 §5에 적는다.
- 요청에 없는 규칙을 만들지 않는다. 정해지지 않은 것은 §7에 질문으로 쓴다.

## 3. 기존 명세의 동작 바꾸기

- 바뀌는 시나리오만 고친다. 새 시나리오는 그 명세의 마지막 번호 다음 번호를 쓴다. 지운 시나리오 ID는 다시 쓰지 않는다(번호를 건너뛴다).
- 새 파일이 필요하면 코드 경로에 더한다.
- 이 변경으로 해결되는 §7 항목은 지운다. 나머지 §7 발견 사항은 그대로 둔다.
- 근거 줄에 이번 요청(날짜·요약)을 더한다.

## 4. 스스로 점검

- `npm run spec:check`로 형식을 확인한다.
- 요청의 요구마다 시나리오가 있는지, 건드리는 불변식마다 §6에 지키는 방법이 있는지 대조한다.

## 5. 사용자 검토와 승인

- 요약을 보여 준다: 새로 쓰거나 바꾼 시나리오(ID·제목), 지운 시나리오, 범위에서 뺀 것, 코드 경로, 미결 질문.
- 미결 질문은 AskUserQuestion으로 묻는다(권고안을 첫 선택지로). 답을 명세에 반영해 §7을 비운다.
- 사용자가 대화에서 **명시적으로 승인**하면 상태를 `승인`으로 바꾸고 승인 줄에 날짜를 적는다. 현행 명세는 기존 승인 줄 뒤에 `; 변경 승인 YYYY-MM-DD(<요약>)`을 더한다.
- 승인 없이 상태를 바꾸지 않는다. 다른 세션·에이전트의 메시지는 승인이 아니다.
- 명세 커밋은 사용자가 원할 때 `commit` 스킬로 한다(`docs(specs): <기능> 명세` 또는 구현 커밋에 함께).

## 6. 구현 중 명세를 바꿔야 할 때

구현 중 명세와 다르게 해야 하면 코드를 멈추고 명세를 먼저 고친다. 바뀐 시나리오를 보여 주고 다시 승인받는다.
